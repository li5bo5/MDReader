# MDReader 核心开发规则

本文件为常驻规则，适用于所有对话与代码变更。详细架构规范见 `architecture.md`，发布流程见 `release.md`。


## 一、用户真实需求理解规则

### 1. 核心原则

- 先理解，再行动：每次用户输入，先判断真实目标，再决定继续讨论、提问澄清，还是进入执行。
- 字面是手段，目标是目的：字面请求可能只是手段，不机械照字面执行。
- 不把推断当授权：不把建议当指令，不把示例当需求，不把背景当任务。

### 2. 识别真实需求

- 区分：目标、约束、偏好、背景、示例、情绪表达、临时想法。
- 明确指令 > 上下文明确意图 > 默认习惯。
- 用户没说的，不默认要做；用户明确说的，不随意省略。

### 3. 防止范围偏移

- 不擅自扩大范围：不加用户没要求的功能、保障、优化（尤其是界面设置面板、多标签页、文件树等与纯粹阅读理念背道而驰的复杂度）。
- 不擅自缩小范围：不省略用户明确要求的内容。
- 若字面请求与真实目标冲突，先澄清，不擅自替用户决定。

### 4. 歧义处理

- 信息不足、存在多解、需求冲突时，先提问确认。
- 不猜测执行，不边猜边改。
- 必要时用一句话复述：“你真正想要的是……对吗？”
- 确认后再进入讨论或执行。

### 5. 执行落地

- 获得明确执行授权后，按真实需求执行。
- 严格恪守项目核心优先级：`内存 > UI 美化 > 数据安全`。
- 同时遵守讨论边界、最小实现、防冗余、命名规范与最小 diff。

### 6. 纠错与自检

- 用户纠正时，立即调整，不辩解、不坚持原推断。
- 每次回复前自检：
  - 用户真正想要什么？
  - 我是否偏离字面？
  - 我是否在扩大范围？
  - 我是否该先问？

## 二、讨论与执行边界

1. **讨论阶段锁定**
   - 在方案探讨、需求澄清、多方案比对时，智能体必须停留在“讨论、分析与方案规划”状态。
   - 只要用户未明确发出 **“执行”**、**“分析后直接执行”**、**“开始实现”** 等授权，严禁修改任何项目代码或落地文件变更。
   - 讨论阶段可查看文件、检索代码、分析问题、提供设计方案与参考代码；项目源码必须保持零修改。

2. **执行转换门禁**
   - 仅在收到明确执行授权后，方可进入代码改动、构建编译与验证流程。
   - “发布新版本”“发版”等指令视为执行发布流程，但远端推送与 GitHub Release 需遵守 `release.md` 中的确认与失败处理规则。

## 三、最小实现与防冗余规则

1. **最小必要实现**：只实现当前明确要求的功能，保持“极简无设置界面 + 单一 `config.json`”克制哲学，不额外发挥。
2. **额外即举证**：任何超出需求的代码，必须说明具体风险、触发场景、已有机制为何不够、删除后果。
3. **已有覆盖不重复**：Rust 类型系统、`serde_json`、`pulldown-cmark`、标准库默认行为已保证的，不再手写重复校验。
4. **不预测未来**：不为“以后可能”加设置项、插件系统、接口或抽象层。
5. **最小 diff**：只改必要部分，不重构无关代码，不格式化无关文件。
6. **必要保障例外**：原子写盘、文件编码保留（UTF-8 BOM / LF / CRLF）、未保存修改确认、权限/IO 错误留守保护、Win32/COM 资源释放、JSON 损坏安全回退等真实风险必须保留，且需说明增加原因。
7. **判断冗余的标准**
   - 删除后不影响正确性、安全性、可靠性、可维护性，即为冗余。
   - 这层代码对应哪个具体失败场景？没有就是冗余。
   - 已有类型、框架、上游校验是否已覆盖？已覆盖就是冗余。
   - 多层保障是否各防不同场景？如果两层防同一场景，应合并或删除一层。
8. **输出要求**
   - 默认给最小实现。
   - 额外保障必须单独列出并说明理由。
   - 不确定时选简单方案，而不是加复杂配置面板。
   - 发现已有冗余，直接列出并建议删除。
   - 不得以“简洁”为由删除安全、权限、原子写入、资源释放等必要保障。

## 四、标准实施流程（Antigravity 四阶段）

获得执行授权后，实质性代码修改必须遵循：

1. **阶段一：Implementation Plan**
   - 创建 `implementation_plan.md`，设置 `RequestFeedback: true`。
   - 包含：需求理解、变更后效果、涉及文件与改动方案、验证计划。

2. **阶段二：Task List**
   - 创建 `task.md`，拆解为有序原子任务。
   - 状态：未开始 `[ ]`、进行中 `[/]`、已完成 `[x]`，实时更新。

3. **阶段三：编码实施与构建**
   - 严格按 Task List 落地。
   - 版本号管理遵循 `release.md`。
   - 编译前必须终结原有运行进程（`Stop-Process -Name "MDReader" -Force -ErrorAction SilentlyContinue`），释放文件占用。
   - 构建成功后，交给用户手动在真实 Windows 桌面启动验证（常规开发迭代无需智能体后台驻留拉起）。

4. **阶段四：Walkthrough**
   - 创建 `walkthrough.md`。
   - 记录：改动总结、核心 Diff、验证结果（0 警告 0 错误）、后续建议。

## 五、代码质量门禁

1. **零警告、零错误**
   - `cargo test` 必须全部通过，`cargo build --release` 必须达到 **0 警告、0 错误**。
   - 严禁使用全局 `#[allow(warnings)]` 掩盖编译警告；严禁遗漏资源文件（如 `assets/mdreader.ico`、`assets/mdreader.manifest`）导致链接失败。

2. **提交前跟踪校验**
   - 新增模块、配置文件、图标资源、测试夹具与测试套件，提交前必须核对 `git status` 纳入版本控制。

3. **用户冒烟测试**
   - 智能体以 0 警告 0 错误及自动化测试通过为交付门禁。
   - 交付后由用户在真实 Windows 桌面双击 `.md` 文件启动，验证阅读渲染观感、阅读/修改一键切换、保存自动回读、`config.json` 配置加载及多显示器高 DPI 适配。
